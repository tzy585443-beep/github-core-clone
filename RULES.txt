Build a GitHub-compatible git forge

## The task
Write a standalone, GitHub-compatible git forge. It runs as one process in the trial's pod, binds an ephemeral port of its own, and serves from its own store with no UI: git smart HTTP (upload-pack protocol v2, receive-pack v0) for clone, fetch and push; the REST v3 API under /api/v3 for repositories, issues, pull requests and contents; the GraphQL v4 API at /api/graphql; and a Model Context Protocol endpoint at /mcp. The suite in the pod is its only client, and a sealed scorer turns the suite's export into your score. Everything it serves is its own: no outside service, no proxy and no git binary.

## The suite and the wire
The suite starts beside your program and waits for it:
1. Your program binds an ephemeral port. Port 0 lets the kernel choose one. It must not bind 8080, where the suite listens.
2. It POSTs {"port": <the port>} to $MAKEFUN_ENV_URL/register.
3. The suite records the address your request came from, dials that address and port, and drives your forge: the conformance checks first, then the four timed workloads.
4. Meanwhile your program long-polls GET $MAKEFUN_ENV_URL/done. The suite answers {"done": false} until it has finished and written its export, then {"done": true}; on that answer your program exits 0.
A program that exits, crashes or never registers before the boot budget ends leaves no working forge and scores 0. A trial still running at its wall is stopped and scores 0 on every column. The suite's base URL is in MAKEFUN_ENV_URL.

## The wire contract
The suite drives four surfaces on your base URL: git smart HTTP at /{owner}/{repo}.git, REST v3 under /api/v3, GraphQL at /api/graphql and MCP at /mcp. Every REST reply is application/json, never HTML, and carries a non-empty X-GitHub-Request-Id header; no X-RateLimit-* header is required. An error carries a JSON body with a string message. The suite presents Authorization: Bearer <token>, the token in your process's MAKEFUN_SHOP_TOKEN; a request without it is 401, and a repository belongs to the login the token names, so the same repository name under another owner is 404, never 403.

The suite drives these requests and requires these replies:
- GET /api/v3/ answers 200 JSON with an X-OAuth-Scopes header
- GET /api/v3/meta answers 200 with a non-empty installed_version string
- GET /api/v3/user/repos answers 200 list; more than one page links the next with a Link header whose rel is "next"
- POST /api/v3/user/repos answers 201, the repository object
- GET /api/v3/repos/{owner}/{repo} answers 200, the repository; 404 JSON when it does not exist
- PATCH /api/v3/repos/{owner}/{repo} answers 200, with the description updated
- DELETE /api/v3/repos/{owner}/{repo} answers 204, and a later GET is 404
- PUT /api/v3/repos/{owner}/{repo}/contents/{path} answers 201 on create, 200 on update, 409 on a stale sha
- DELETE /api/v3/repos/{owner}/{repo}/contents/{path} answers 200 {commit:{sha}}, 404 on a later GET
- POST /api/v3/repos/{owner}/{repo}/labels answers 201 {name}; a label must be created here before an issue may carry it
- POST /api/v3/repos/{owner}/{repo}/issues answers 201, an open issue; 422 when it names a label that does not exist
- POST /api/v3/repos/{owner}/{repo}/pulls answers 201, state open, with head and base
- GET /api/v3/repos/{owner}/{repo}/pulls/{number} answers 200, the pull request; 404 when unknown
- PUT /api/v3/repos/{owner}/{repo}/pulls/{number}/merge answers 200 {sha, merged:true, message}: the pull is closed and merged, and its squash commit is on the default branch; 404 for an unknown pull request, 405 for a conflicted one
- any unknown route answers 404 JSON, never HTML
- any malformed JSON body answers 400

## Git over smart HTTP
A repository is created through REST (POST /api/v3/user/repos): a push cannot invent one. Its remote is <base URL>/<owner>/<repo>.git, and the suite speaks the smart-HTTP protocol in process, with no git binary in the pod. upload-pack must speak protocol v2 (the suite requests it with Git-Protocol: version=2): the v2 capability advertisement and both ls-refs checks require it, and a v0 answer loses those three while the rest of the checks fall back to v0. receive-pack is v0 only, and must advertise report-status, side-band-64k and delete-refs. A v0 upload-pack that does not advertise side-band-64k cannot be framed. The v0 upload-pack and receive-pack advertisements open with the "# service=git-upload-pack" and "# service=git-receive-pack" preamble; the v2 advertisement opens with "version 2". A missing repository is 404 on both services' GET /info/refs, and the server stays up. Every update must fast-forward: a non-fast-forward push is refused per ref with "ng <ref> non-fast-forward" and the ref does not move, and the suite never force-pushes. A push carrying one fast-forward and one refused ref applies the fast-forward ref and answers one report line each: ok for the first, ng non-fast-forward for the second.

## GraphQL
POST /api/graphql takes {"query": ..., "variables": {...}} with the trial's bearer token; an unauthenticated request is exactly 401. The suite sends the documents gh and github-mcp-server send, and introspection must describe them: __type(name: "Issue") lists id, number, title, state and body; __type(name: "PullRequest") lists id, number, headRefName, baseRefName, mergeable, state, merged and files; __type(name: "Repository") lists id, databaseId, name, nameWithOwner, owner, defaultBranchRef, viewerPermission, hasIssuesEnabled, issue, issues, pullRequests and pullRequest; and SearchType's enumValues include ISSUE. repository.issues with orderBy: {field: CREATED_AT, direction: DESC} returns issue numbers in descending order, ties by number DESC, and states: [OPEN] omits closed issues. createPullRequest takes a repository id and a head branch pushed over git, and opens a pull request REST reads back with the same head and base refs. Two operation documents in one body answer two results in order; a query naming an unknown field is HTTP 200 with an errors array naming it; an unknown repository is data.repository = null with no errors.

## MCP
POST /mcp is JSON-RPC 2.0 over the Streamable HTTP transport, answering application/json or text/event-stream (SSE), and each request must answer inside 3 seconds. It speaks revision 2026-07-28 (every request declares it, and server/discover answers a result whose supportedVersions is a non-empty list of YYYY-MM-DD revisions), or a handshake revision (2025-11-25 or earlier) through initialize and notifications/initialized with an optional Mcp-Session-Id. tools/list offers at least six tools, including create_repo, get_repo, create_issue, list_issues, create_pull_request and merge_pull_request; a server prefix on a name is allowed (github__create_issue), matched as a suffix and case-insensitively; every tool has a non-empty description and an inputSchema of type object, and two tools/list calls answer the same list, byte for byte. Two tools/call requests in flight keep their own JSON-RPC ids and answer for their own arguments. The suite calls them with the arguments github-mcp-server documents: create_repo {name}, get_repo {owner, repo}, create_issue {owner, repo, title, body?}, list_issues {owner, repo, state?}, create_pull_request {owner, repo, title, head, base} and merge_pull_request {owner, repo, pull_number}; it maps each argument onto your schema's nearest property name and fills a full_name property with owner/repo. An unknown tool answers JSON-RPC -32602 or -32601, never HTTP 500; a tools/call missing a required argument answers isError:true or -32602; a body that is not JSON answers HTTP 400 with -32700 (200 with -32700 from a server that predates 2026-07-28); a call with no Authorization header answers 401. The tools act on the same store as REST: a repository and an issue created over MCP read back over /api/v3 as the same objects, their ids unchanged across reads.

## What is scored
Your score adds three columns, from 0 to 1,000:
- Feature checks, 600 points: round(600 x passed / total) over the suite's conformance checks, each pass or fail.
- Agent-native, 200 points: round(200 x passed / total) over the suite's MCP checks, the initialize, tools/list and tools/call surface an agent uses.
- Performance, 200 points: the four timed workloads below, each worth at most 50 points, summed to a whole number.
The leaderboard shows each column beside the score, and the score decides the places: they go by score, highest first, so the highest score wins 1st place. It also shows Works, 1 when the trial's forge came up and answered and 0 when it did not, which decides no score and no place. A trial's state export holds only pass/fail bits and counts, never a time, a port or a date, so a replay compares two runs of it byte for byte; the timings go in a separate performance export.

## The performance workloads
Four workloads, each the wall time of a fixed amount of work, the median of 3 rounds, after 5 untimed warm-up operations and with every input built before the clock starts:
- push: 200 pushes of a 1 KiB change to one repository, one after another.
- clone: 50 concurrent shallow clones (depth 1) of a 200-commit repository.
- read: 2,000 GET /repos/{owner}/{repo}/issues/{number} calls, one after another, on one keep-alive connection.
- write: 200 issue creations, one after another.
Each workload's points are clamp(25 - 12.5 x log2(t / T_ref), 0, 50), rounded to a whole number, where t is its median in milliseconds and T_ref is the house reference forge's own median for that workload, measured on the production sandbox before entries opened and published in the kit's calibration file. A time at T_ref scores 25 points, half of T_ref 38, double 13, and a quarter or less 50. A workload that cannot finish in its budget scores 0 and stops early.
The tie-break column, perf_p50_us, is 1,000 times the geometric mean of the four workloads' medians in milliseconds, in whole microseconds; lower is faster.

## Trials, instances and the final
- Practice: 3 practice instances are drawn by the sealed generator from a public drand quicknet round emitted before the competition opened and are published in the kit. Each submission runs one trial, live only, on the first practice instance; its score shows as it lands.
- Final: 3 scored instances are drawn by the same generator from the first drand quicknet round emitted at or after the final phase starts, 10 minutes after the deadline, the same for every entry. Nobody, the organisers included, can know them while entries are taken.
- The final is staged. Every final entry runs one trial on the first scored instance, live: its qualifying trial. The 60 entries with the highest scores there, and every entry tied with the 60th, go on; the house's entries and the house baseline always go on and take none of the 60. An entry that goes on, a contender, runs one trial on each of the 3 instances, its qualifying trial the first of them, and each of its 3 trials is replayed.
- Contenders rank on their mean score over the 3; every paid place goes to a contender. An entry that stopped at its qualifying trial ranks below every contender, by its score there.
- Every trial of a contender runs twice: live, then replayed. The replay must leave the same state export, byte for byte, and an entry whose two exports differ is listed and unranked. A practice trial, and the qualifying trial of an entry that does not go on, run once, live, with no replay.
- A trial whose program is still running after 900 seconds is stopped and scores 0 on every column.

## A trial
Each trial runs three containers on a network of their own: the agent, the env (alias store: program/env/, seeded from the instance's input/env/) and the gateway (alias llm). The network has no route out: the agent has no network but the two services. Only the gateway reaches further, and only to the model provider. Everything binds 0.0.0.0. The agent's repository is at /bot, read-only; /input holds only prompt.txt; stdin is closed; the limits are 2 CPU, 1024 MB of memory, 256 processes and a wall budget of 900 s (15 min). Its environment holds, of ours, exactly these variables:

  MAKEFUN_PROMPT_FILE       /input/prompt.txt: the brief, the one file the agent reads
  MAKEFUN_SHOP_GRAPHQL_URL  http://store:8080/admin/api/2026-10/graphql.json: a store env's Admin GraphQL endpoint (POST)
  MAKEFUN_SHOP_TOKEN        the token a store env's endpoint takes, as X-Shopify-Access-Token
  MAKEFUN_SUPPLIER_URL      http://store:8080/supplier/v1: a store env's supplier REST API
  MAKEFUN_TRIAL_SEED        the trial's seed: seed every random choice from it
  MAKEFUN_TRIAL_NOW         the instance's opening time: the env's every timestamp, and the only now a request may carry
  MAKEFUN_ENV_URL           http://store:8080: the contest environment's origin, the same in every trial
  ANTHROPIC_BASE_URL        http://llm:8080: the gateway, for Anthropic Messages
  OPENAI_BASE_URL           http://llm:8080/v1: the gateway, for OpenAI Chat Completions and Responses
  ANTHROPIC_API_KEY         makefun-trial-<48 hex>: a stand-in key derived from the trial, the same on its live pass, its replay and every regrade; read it from here: the gateway answers no other key and holds the real one
  OPENAI_API_KEY            the same stand-in key

This competition's env is not a store env: MAKEFUN_SHOP_GRAPHQL_URL, MAKEFUN_SHOP_TOKEN and MAKEFUN_SUPPLIER_URL, which every agent/v1 trial sets, are a store's, and the rules above say what this env serves at MAKEFUN_ENV_URL. The token, the seed and the now derive from the instance and the trial alone, so both passes of a trial see the same values. The model SDKs read their base URLs and keys from these variables; nothing proxies (no HTTP_PROXY: Node's fetch would ignore it).

## The determinism rule
Every final trial of an entry that goes on to all the scored instances runs twice, its first trial too once the cut sends it on, on the same instance with the same variables; the first trial of an entry the cut stops there runs once, LIVE alone, and is scored as it ran (as a dev trial runs once, LIVE alone, so a practice score never says whether its replay would match: grade-local runs that replay for you). LIVE: the agent runs, and the gateway forwards each model call to the provider, meters it and records it, its answer byte for byte, in the trial's cassette. REPLAY: the agent runs again, and the gateway answers each call from the cassette with no provider behind it, matching a request by its content: its route, its anthropic-version, anthropic-beta and openai-beta headers and its JSON body (no other header, so an SDK's retry counter never matters). The replay must make exactly the live pass's requests (the first the cassette does not hold stops the agent; one left unmade fails the replay too) and leave the env's state.json, its canonical export, byte for byte as the live pass left it. A trial whose replay does not match is nondeterministic, and so is its run: listed, never ranked. So nothing that differs between two runs may reach a request, to a model or the env:
- no wall clock: never Date.now(), new Date() or a timer's reading in a request; take dates from MAKEFUN_TRIAL_NOW;
- no unseeded randomness: never Math.random() or a random UUID; draw from MAKEFUN_TRIAL_SEED;
- one order: send the env one request at a time, in the order they were made. Model calls may run in parallel (the replay serves identical requests in their recorded order), but what the agent does with the answers must not depend on which came back first.
Waiting is fine; a time must never be written into anything sent. The SDK in sdk/ keeps the first two for you (trialNow, trialRng); the one order is your agent's to keep.

## Models and budget
Allowed models (the request's model must match one; * any run of characters, ? one): claude-haiku-5-5, gpt-6-luna. GET /v1/models on the gateway answers the list. Every call is priced at its recorded time on the pricing rows kit.json's pricing_rev names, and a trial may spend $0.02 on at most 20 requests, each asking for at most 1024 output tokens in a body of at most 262144 bytes (256 KiB). The gateway checks every call before it forwards one, and the first check that fails refuses it in the provider's own error shape (so an SDK raises its usual error), with x-should-retry: false and what is left of the budget. A refusal is a cassette entry like any answer, so the replay refuses it the same way:

  request_too_large 413    a body over 262144 bytes (256 KiB)
  invalid_json 400         a body that is not a JSON object
  stateful_request 400     a request leaning on state kept at the provider (a previous response, a stored conversation, store: true, an uploaded file, a container): a trial carries no state in or out
  model_not_allowed 400    a model matching none of the allowlist (claude-haiku-5-5, gpt-6-luna), or one with no price
  max_tokens_required 400  no output cap (max_tokens; max_completion_tokens or max_tokens; max_output_tokens), or one over 1024 tokens
  request_cap 429          past 20 requests in the trial
  budget_exhausted 429     a request whose worst case (its input at a token per 3 bytes and the model's dearest input rate, its whole output cap), with what the trial spent and has in flight, would pass $0.02 a trial

A spent budget ends nothing by itself: the env's state is scored as it stands when the agent exits. Streamed OpenAI Chat Completions are forwarded with stream_options.include_usage set, so each carries its usage (one extra final chunk).

Who pays: an entrant's model calls run on its own model provider API key, pushed to the competition apart from the entry as an entry secret (ANTHROPIC_API_KEY, OPENAI_API_KEY or GEMINI_API_KEY), and the gateway forwards them to the provider on it; make.fun pays for none of them, and the house's own entries alone run on house money. An entry holds no key of its own: the key variables above carry the stand-in, and an entry whose files hold a provider's API key is refused.

Nothing of a trial is kept at the provider: OpenAI Responses calls are forwarded with store: false, and store: true is refused (stateful_request) on Responses and Chat Completions alike. So pass a reasoning item back whole, asking for it with include: ["reasoning.encrypted_content"], never by its id alone: the provider answers that with a 400 ("Items are not persisted when store is set to false"), which counts as the entry's own error, not the provider's.

## Trials and how they count
The final is staged: every entry runs the first scored instance once; the top 60 by its score there, and anyone tied with the 60th, run all 3 instances, each trial replayed; they rank on their mean over the 3, and the rest rank below them. The scored round draws the 3 instances, the same 3 for every entry, and the first is the one every entry runs. An entrant whose first trial runs out of its wall time does not go on. The house's own entries and the baselines always run all 3, whatever their first trial scored, and take none of the 60 seats. On the dev phase each submission runs one, on practice/trial-0/. When the agent exits the env exports its state, and program/scorer/ scores that export (at /output) against the instance's reference/ (at /reference), writing scores.json: an integer for each scored column.

  score        Score: the rank key, a run ranks on its mean over the trials
  feature      Conformance
  agent        Agent native
  perf         Speed points
  perf_p50_us  Median time (us)
  working      Works: 1 or 0 for each trial, as the scorer decides

How a trial ends:

  finished          the agent exited (a crash or a spent budget too) and, on a final trial that is replayed, the replay matched: its state is scored
  timeout           the wall budget ran out: 0 on every column
  nondeterministic  the replay did not match: the run is listed, never ranked
  void              a fault that is never the agent's (the sandbox, the env, the gateway, the scorer, or upstream errors on 20% of the trial's forwarded requests, at least 3): it runs again on the same instance, and never counts

A run's value in each column is the mean of its trials', with the 90% t-interval on the rank key; a run with no nondeterministic trial is ranked. Two runs tie when the 90% paired t-interval of their per-instance differences on the rank key contains 0, and the ranking stands. Exact ties on the rank key score go to the lower Median time (us) (perf_p50_us), then the earlier receipt. A placement prize needs a rank value better than every published house baseline's. What earns the points is the competition's: its rules above, the brief in each instance's input/prompt.txt, and program/scorer/, the exact code that scores.

## Secrets (optional)
Secrets are never required: an entry whose entrant pushed none is taken and graded like any other, every model call it makes answered 401 (no provider key).

If your entry needs one, put it in a .env file as a NAME=value line and push the file to this competition, signed in (Enter, step 2), from this directory:

  node cli/makefun.mjs secrets push github-core-clone-01 --env-file .env

--stdin in place of --env-file reads the lines from standard input, and --dry-run prints what it would send (each name, its lane and size, never a value) and sends nothing. A value never goes on a command line, which a shell's history and an agent's transcript keep, and no MCP tool takes one. A push sets every name it holds and leaves your other secrets as they are: at most 16 secrets, each value 8 characters to 8192 bytes (a shorter value is too short to mask: keep it in your repository's config). PUT /api/competitions/github-core-clone-01/secrets takes {"secrets": {"NAME": "value"}} with your API key too. node cli/makefun.mjs secrets ls github-core-clone-01 shows what make.fun holds (names, lanes and hints, never a value), and node cli/makefun.mjs secrets rm github-core-clone-01 <NAME> removes one. grade-local, with --env-file .env added to its command under Grade locally (above), runs your entry here on the file's secrets as make.fun's runs of it get them: it reads the file as a push does, never a value on its command line, and what it prints and keeps names the secrets alone.

A value never belongs in your repository or your transcripts. make.fun stores every entry's code with its whole history, so an entry whose repository holds a value you pushed, in any commit's files or message and in any encoding, is refused (committed_secret): rotate it, push the new value and purge the old one from the history. The check under Before you submit, run with --env-file .env added, looks there first for every form of each value of the file. A transcript holding one is masked before anything of it is stored, and never refused; a run whose outputs hold one (its state, output files or action log, scored byte for byte and so never masked) keeps its score, and make.fun withholds those outputs from every copy it publishes. Never commit a provider key either: an entry whose files hold one is refused (committed_provider_key).

ANTHROPIC_API_KEY, OPENAI_API_KEY and GEMINI_API_KEY (or GOOGLE_API_KEY) are provider keys: they reach a model only through the gateway, which forwards your entry's model calls to the provider on them within the per-trial budget, and their values never enter the sandbox, where those variables carry the stand-in. A Gemini model is called on the OpenAI-compatible route, through OPENAI_BASE_URL. make.fun pays for none of an entrant's model calls. This competition's allowed models are served by Anthropic or OpenAI keys: push ANTHROPIC_API_KEY or OPENAI_API_KEY for them. Its provider checks a pushed key first by listing its models, which spends nothing and refuses nothing (a key it refuses is stored all the same), and only its hint, its prefix and last 4 characters, is ever shown again. If its provider refuses your key when a final-phase trial is about to run, that trial waits for you to push a working one, never past the final phase's end: the entry's status shows a push_secrets step with its deadline, and the trial scores 0 if none is pushed by then. On the dev phase a refused key scores the trial 0 at once.

Every other name becomes an environment variable of your entry at make.fun's runs of it, on the live pass of every trial and the replay pass of every final trial alike, and of nothing else: never the scorer, the env or any program of make.fun's. An L2 regrade re-runs it with the same values while they are kept; once they are erased it is refused, and the L1 regrade, from the run's own record, stands. A reserved name (PATH, HOME, NODE_OPTIONS, LD_PRELOAD, PYTHONPATH, any GIT_*, MAKEFUN_* or MAKE_* name, and every variable the harness sets) is refused, and only a value's byte length is ever shown.

The sandbox reaches nothing outside but the env and the gateway to the models, so a secret for an outside service cannot be used: one serves only code that runs inside it, such as a key that decrypts a file your entry ships.

Each value is sealed to make.fun's grader when it is pushed, and erased once this competition's challenge window ends. A value you replace or remove reaches no run from then on and is erased at once, unless a final-phase run of your entry ran with it: make.fun keeps that one sealed until the challenge window closes, so a challenge can re-run that run, then erases it.

   From then on submit signs make.fun entry v2 with wallet.json, naming W, and every prize pays W, which claims it signed in with W. The pin stays until W releases it (revoke --delegation <sha256> --keypair <W's keypair> --then release); revoke's default, hold, ends one delegation and keeps the pin. Once every delegation of W for the account has expired (and W holds none), the account clears the pin itself (delegate clear --payout <W> --keypair wallet.json); an admin can clear it too.

## The claim file
The repository must be yours: its GitHub owner is your account's GitHub login, or it holds .makefun/owner.json at the submitted commit, naming a wallet on your account (the one register or login signed in with, or one wallet add --keypair <file> added). .makefun/owner.json is in no starter: an account with no GitHub login (a wallet-only one, as register makes) always needs it, committed with the entry:

  {"wallet": "<base58 address>"}

A source bundle entry (step 5 of Enter) needs no claim file: the wallet its root's .makefun/freshness.json names, on your account, proves the repository yours.

## The transcript gate
To keep every bounty fair, an entry is valid only with the transcripts of the agent sessions that built it, which show that the entrant's own agent built it: one without them is rejected, unless its competition makes them optional.

make.fun asks for the transcripts to keep every bounty fair: they show that the entrant's own agent built the entry, not someone else's work or existing open-source code passed off as theirs. The thinking checks match the code against the sessions that wrote it. They are never published, a winner's included: only the entrant's account and make.fun's admins can read them, and secrets, e-mail addresses, home folder names and usernames are stripped from them before anything is stored.

The instruction files and the system prompt are no part of this gate. An entry is never rejected for leaving them out. With no system prompt and no instruction file, bundle prints a warning and a reviewer sees a note that the instructions were not uploaded; the checks and the grade are the same.

This competition requires them: every entry uploads them, and they pass these checks before it is graded. Each is pass or fail, never a score: a fail rejects the entry with the check's fix, and a new entry can pass before the deadline. The checks this competition runs, and their thresholds:

  transcripts_present   No transcripts parsed
  transcripts_recorded  handed_over_places none
  thinking_wellformed   max_step_back_sec 60
  thinking_in_window    clock_skew_sec 60
  thinking_reproduces   min_reproduced 0.3 (30%); entrypoints main.ts, main.py
  thinking_turns        min_assistant_turns 5
  thinking_priced       min_priced_share 1 (100%); min_self_reported_usage_share 0.5 (50%); max_self_reported_tokens_per_sec 500; min_muse_app_usage_rows 1
  thinking_revised      min_file_writes 2
  thinking_fresh        min_fresh_share 1 (100%); clock_skew_sec 60

- transcripts_recorded: every session is a log a harness recorded or a file exported from its record; a session your agent hands over because its tool keeps no session record (a session file it exported itself carrying "handed_over", one line saying why) makes this check skip as a note naming it, never a rejection, and the entry's build cost is labelled Handed over; under handed_over_places none: An entry with a handed-over session is ranked where it scores but takes no paid place: to compete for rewards, tell the person you work for to run you in a client whose sessions are recorded. If you cannot hand over what you can see, use Superbot (https://superbot.gg), a free client: run on your own computer, it keeps sessions that bundle reads.
- thinking_wellformed: every user, assistant and tool message of a session carries a timestamp (a handed-over session's messages may carry none, and the times they carry are held to the rest), no assistant or tool message falls more than 60 s behind the latest before it, and every tool result answers one earlier tool call of its session; a session file your agent exported itself names the harness that wrote it, in the file or with bundle's --harness.
- thinking_in_window: every transcript timestamp lies between the competition's opening and the entry's receipt time, give or take 60 s of clock skew.
- thinking_reproduces: the transcripts account for at least 30% of the counted lines (authored or pasted), and the entrypoint (main.ts or main.py) has at least one authored line; a packed entrypoint the kit's makefun compress wrote counts as the source it was packed from, which bundle uploads beside the sessions, when makefun compress makes the entrypoint from that source byte for byte and the sessions show the agent writing the source and then running makefun compress on it later than the latest message in which one of the source's authored lines first appears (an edit that only deletes or re-types lines is no write), shown by the agent's own command running makefun compress on the source or by the line makefun compress prints, in a tool result or any other message; the source's lines then count toward the share as any counted file's do, a line repeated in it counted once.
- thinking_turns: at least 5 assistant turns carry text or thinking (a turn that only calls tools does not count).
- thinking_priced: every usage record prices to a known model, or to $0 where the record's session ran its model on your own machine (a local runtime or loopback server the session records, never a model's name or a self-export's stated provider), for this check alone, never the entry's build cost; a self-reported session (a file exported afterwards, not a log a known harness wrote; a file in Claude Code's or Muse Code's session format without the token usage those harnesses record on every response, or in Claude Code's without its version, is one) carries the provider's usage on at least 50% of its assistant messages, with the provider's own token counts, not rounded, estimated or repeated figures (a provider's input count grows as the conversation does, so one pair of counts does not keep coming back), and its output is no more than a model produces in the time its own timestamps span (500 tokens a second); a handed-over session need not carry usage, but the usage it does carry is held to the same rules; an upload of harness-recorded logs with no usage has nothing to price; an entry whose sessions are the Muse app's own session files carries its agent's token usage as Muse recorded it (at least one usage row across them), attached with bundle's --muse-usage.
- thinking_revised: some file (the entrypoint, or the code it runs) takes its final content from at least 2 assistant messages that write or edit it (a file written once in full and never revised counts 1).
- thinking_fresh: for an entry uploaded as a source bundle, every credited line comes from agent sessions that show the anchor line the kit's init prints (makefun anchor <root sha> round <round>) in a tool result before their first counted write (a Claude subagent launched after its parent's quote, or a Codex fork of a session that quoted it, counts with it); short of that the check skips as a note: the entry is not rejected, and its reward, if it places, is paid as any other. A quote timestamped before the round fails.

## The harness
harness/harness-src.tar.gz (sha256 6b59c0155fefd3e232b10a7568d148eafaa3dfe732ea3d24accc4e481792e024) holds the harness source exactly as this server runs it: every .ts, .json and .sh file of grader/, sim/, contracts/, pricing/, server/blobstore.ts and server/repos/index-tar.ts.
harness/SOURCES.sha256 lists every file's sha256 (`sha256sum -c` checks the unpacked tarball against it).
harness_version in kit.json is "harness@<digest> node <version>", where <digest> is the sha256 of the lines
"<path>\0<code sum>\n" for every file listed in harness/CODE.sha256, in that order. A file's code sum is the sha256
of its code (grader/version.ts codeSha256): a .ts file's text with its comments and the whitespace between its tokens
dropped (tsCode), a .json or .sh file's bytes. An edit to comments or whitespace alone names no new harness_version.
